# Default source policy correction

The revised defaults admit strict UTF-8 source text and the observed document
text extensions up to 32 MiB. Existing roots change only through explicit
configuration application. Source scope, protected locations, physical identity,
checksum validation, no-follow/no-recall reads and unsupported reparse rejection
remain enforced.

Retained Office extraction accepts blank spreadsheet cells and uses finite XML
capacity limits. Media metadata streams retained input up to 1 GiB under a
96 MiB read budget. ZIP/TAR defaults are 128 MiB compressed input, 256 MiB total
expanded data and 32 MiB per member. ZIP nesting is limited to two levels sharing
the total budgets. Long C# signatures retain a bounded display and full-value
hash after disclosure checks; parsing never executes source code.

The explicit native `policy_reprocess` action binds one root configuration,
revision, predecessor and retained checksum. Application uses serialised SQL
fences, versioned successor lineage and audit receipts. It neither rescans the
workspace nor hydrates source originals. Missing or changed retained content
refuses admission. Original terminal evidence and last good publication are
preserved. Rescans reuse the admitted text successor; unlinked previous pending
text is cancelled with successor evidence. Configuration drift produces visible
`policy-binding-stale` status. Only never-executed successors without a lease,
attempt or pipeline result can have their proof refreshed.

Changed processors register new immutable capability identities. Exact previous
descriptor pairs remain readable. Before an ordinary incremental deployment can
release its validation hold, readiness proves that no older processor has
pending/running branches, branchless runnable activities or outstanding force
requests. A refusal leaves the hold/rollback safeguards in charge; it is not
permission to migrate or discard work.

Automatic predecessor rollback ends when the updater attempts to release its
validation hold. Ordinary workers may write immediately after release, before
explicit policy admission. After that boundary, restoring old binaries alone
can strand new processor identities: reconcile the exact release and use a
reviewed compatible recovery or forward correction.
No schema migration, full clean-slate deployment or model acquisition is required.

Unsupported RAR/7z and database sidecar content remain deferred by capability.
Unsafe archive paths, checksum failures, Visio package safety limits, unavailable
cloud content and unresolved GPU ownership remain limitations. Raising a policy
bound does not imply a parser, a safe package or confirmed execution ownership.
