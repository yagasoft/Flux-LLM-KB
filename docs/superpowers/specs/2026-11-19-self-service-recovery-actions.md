# Self-service recovery action inventory

This is the implementation scope for the [self-service recovery design](2026-11-19-self-service-indexing-recovery-design.md), based on the shared restoration checkpoint at 5c99e918. Implement the listed actions, status and refusal paths in one delivery. Availability is decided by the owning service using current evidence on the selected target. A reason label identifies what to investigate and cannot authorise a mutation.

## Automatic actions and continuations

Connect existing automatic behaviour to the issue inspector and Activity only where the owning service provides attributable evidence. Reuse the worker that already owns the operation. An ordinary scheduled attempt or fallback is shown as such. A stale input or historical label authorises no action.

| Situation | App behaviour and eligibility |
| --- | --- |
| Changed source item, interrupted scan, queued source scan, or source retry that is due | Continue native watcher, reconciliation, source startup and scan recovery. Use current source authority, configuration and scan ownership. Show what is scheduled, whether a provider or journal fallback is in use, and when it last made progress. A paused or disabled source and parked retry debt go to guided review. |
| Temporary source access denial on an approved root | Surface the existing scoped access helper's attempt and verified result. Its installed policy must authorise the exact physical root and identity. Explicit denies, unsupported ACLs, unsafe paths, changed identities or an unavailable helper go to guided action. |
| A CPU delivery or processor attempt has a recoverable existing claim | Let the owning outbox or processor path reclaim a fenced delivery, or restore proven abandoned work, under its existing admission and attempt rules. Show the actual reclaim or deferral. A stale processing label without an exact matching delivery is guided evidence review. |
| A GPU dispatch is pending, a result has been durably recorded, or the scheduler can prove no start or cleanup | Let the native scheduler and adapter deliver the existing dispatch, finish recording an already-owned result, settle the exact slot, or continue the exact checkpoint where the adapter already permits it. Show result and resource release independently. Interactive search can settle proven owner exit and release capacity, and never replays the user's search. |
| Publish is waiting on a changed corpus snapshot or free index storage | Surface the existing fenced Publish deferral, last attempt and next retry. After repeated failure show the blocker and the applicable guided fix without adding a second retry schedule. A terminal Publish job remains guided. Existing exact-target retry eligibility does not establish why a terminal failure occurred. |
| Current index projection needs bounded repair, or selected Git publication can be restored | Surface the existing derived-index and repository recovery owners and their progress. Continue only those existing proofs and budgets. If recovery reaches Operator action required, show the exact reason and route to diagnostics. |
| Source removal, supersession, or Outlook capture already has an authorised active operation | Show the owning service's continuation and result under its existing rules. Approval to run one operation applies to that operation's existing scope. A new deletion, a new capture/catch-up, and an authorised cleanup that stops for review use guided flows. |

## New automation candidates

These are implementation candidates, not existing automatic capabilities. Both have guided implementations in this delivery. Enable an automatic path only if the isolated app proves a normal positive case from the owning service, with fresh commit-time evidence, a single durable budget claim, safe resumption after process loss and strict refusal under concurrency. Where the application cannot obtain that proof, the case remains guided or reports a missing prerequisite. Fresh target-specific approval is required before enabling a qualified production policy.

| Situation | Candidate and additional proof |
| --- | --- |
| A current Embed job is terminal after a settled attempt without a verified result | **Candidate for automatic retry.** Apply the design's strict terminal Embed allowlist and reuse the existing retry transaction. Require the exact draft and unresolved input group, terminal dispatch, proven native cleanup, released capacity, current source and no competing writer. The stage gets at most one new automatic requeue, subject to its tighter existing input-group limit. Missing checkpoint evidence, uncertain delivery, exhausted budget, unavailable input and pre-draft failures go to guided review. |
| The exact PDF or image revision is current and admissible again after OCR stopped during loss of source authority | **Candidate for an automatic exact successor.** Restrict launch to the existing `document-ocr-source-withdrawn` no-result settlement and the full current retained-document proof. Require fresh exact-target physical observation plus current authoritative inventory or capture for the same retained revision. Bind the root configuration and current authority and recheck them under the successor fence. Where the policy needs unchanged configuration since settlement, require a durable link between the old and current configurations. Prove the normal remove, reconcile, restore and rescan path in an isolated positive case. Direct edits to suppression state cannot establish this. Refuse timing-based inference, changed input, replacement, suppression and pause. Recovery itself never unsuppresses a source. Require a terminal dispatch and released batch, trusted OwnedJobEmpty cleanup for that execution, and no result receipt or competing work. Preserve the existing one-successor relation on the original retained parent revision across automatic and guided submissions. The budget is shared across child records, branch replacement, restarts and hosts. Record the actual actor surface on the native audit event. Keep generic runtime exit, other cleanup reasons, resource limits, provider errors and terminal parser failures in guided review. |

### Qualification results

The new terminal Embed retry remains guided. The existing executor uses its bounded checkpoint continuation after cleanup. A missing result leaves the native delivery uncertain even when scheduler capacity is released. Three failed attempts of the same input group exhaust the existing budget. The isolated SQL tests cover that path and the rejection of replayed prior deliveries.

The new OCR successor also remains guided. The current settlement proves cleanup of the exact execution and release of the batch. It does not capture the physical source and root configuration at withdrawal, and a later scan can associate a same-byte replacement with a prior retained revision. The isolated guided fixture validates the exact native successor, but does not establish automatic eligibility through normal physical withdrawal and rediscovery.

## Guided actions

Group these by cause and affected source on Overview. Open the exact item or scoped group and present impact, readiness, preview, confirmation, receipt and downstream progress. A group is a way to find the affected items. Use each native operation's existing scope and confirmation contract, with server-side capability checks, target versions and durable idempotency.

| Situation | Action and boundary |
| --- | --- |
| Overview status is stale or unavailable | Refresh status. Show the last successful sample and recency. Keep status refresh separate from restarting or retrying indexing. |
| A source is paused or work is waiting for an operator | Preview and resume the selected source if authorised, or show the named hold and the next eligible step. Direct the user to pending changes and source status. Maintenance and validation holds protect all affected mutations. |
| Pending change, outdated metadata, scan error or exhausted source scan retry | Offer Process pending changes, Reconcile metadata, or Retry scan according to the exact source and scan state. Reuse the existing scan request and delivery fences. Add the current root, configuration and pause/admission check inside the retry transaction before exposing Retry scan. Display the difference in scope and attest only after readback. |
| Item is cloud-only, in use, moved, inaccessible, or on an unapproved volume | Show the specific prerequisite and relevant source details; after the prerequisite, offer the narrowly eligible pending-change or metadata action. Link to reviewed USN volume management where applicable. Changes to Windows ACLs, helper policy, physical source authority, credentials and provider hydration require the appropriate owner. The dashboard provides the evidence and next step. |
| Source policy excluded an otherwise supported item | Review the relevant source rules, preview an eligible policy change and its reconciliation scope, or request exact retained-policy reprocessing for an eligible existing item. Use existing processor capability checks for Retry and Policy override. Provide Ignore/Unignore as an attention-list preference, visibly separate from remediation. |
| Existing retained document has a settled failure or supports reprocessing with a changed processor | Preview the exact retained revision and processor, show why it is eligible, and queue one supported successor. Cover eligible PDF and image recovery and the prepared Visio path. Reuse the exact server-side proof behind the trusted-local command, with an authenticated dashboard capability, native preview/confirmation and truthful actor-surface attribution. Preserve prior execution, input, result and publication evidence. Where the only current path requires stopped maintenance, show its prerequisite and use the authorised maintenance flow. |
| An archive branch has a supported processor failure or UTF-8 misclassification | Offer the exact permitted branch retry or ZIP member reconciliation; Preview the whole selected archive branch for the encoding-reconciliation command. Display an affected member if the attempt evidence identifies it. Retain the native scope, loopback, origin and antiforgery checks. An unsafe archive or unsupported parser gets an explanation and a supported input replacement path. |
| Terminal Embed or Publish job is eligible on current evidence | Offer Retry embedding or Retry publication using its exact existing action. Show whether checkpoint, published data or completed inputs are reused and report progress to searchable publication. Never turn historical status, a broad “GPU uncertain” label or an unknown Publish timeout into a blanket retry. |
| CPU claim, GPU result, or native resource ownership cannot be confirmed | Offer Check recovery evidence. Identify the missing delivery, owner or cleanup proof and link to the exact job, task and event trail. Offer a repair only once the owning service can prove an eligible settlement or successor. An unconfirmed live owner blocks competing work even after an operator confirms the preview. |
| Publication is blocked on free space or the derived index needs operator attention | Show the space/configuration problem and relevant index health. Offer narrowly scoped restore or retention review where the existing native action supports it. Carry the operation's separate approval and rollback requirements into the review. A rebuild, production restart, destructive removal or recovery archive retirement requires its own authorised operation. |
| An Outlook profile needs attention | Link to the affected profile and show its pause, access, companion or catch-up status. Guide the user to verify the scope, edit or resume the existing profile, and preview a bounded catch-up. Confirmation checks the profile revision and current folder IDs. The companion uses the profile configuration at claim time. The received-time action covers the configured overlap; older moved messages can still be missed. Follow the exact catch-up receipt, then use source progress for its indexing result. |
| An existing source removal has stopped | Show the exact cleanup phase and evidence. When the existing lifecycle permits it, offer the guarded Retry cleanup flow for that same removal under its existing approval and source scope. Earlier records are available in History and confer no recovery authority. |

## Cases that need a prerequisite

Provider hydration, authorised unlocking or re-export, supported format or parser, unsafe path or archive, document size or decoded-memory limits, a missing approved local model or runtime, conflicts with another live owner, missing native cleanup or current input evidence, and an unknown failure all need a reason-specific next step. Show what is missing and a route to the closest existing screen or actionable diagnostics. Refresh re-evaluates eligibility after the prerequisite has been met. This design includes no dead-letter replay, blanket source replay, production administration bypass, automatic download or global clearing of uncertainty.

## Verification

Cover each row through its normal user-facing route, using isolated or synthetic fixtures where necessary. Automatic retry tests must prove positive eligibility, refusal without exact proof, durable one-attempt limits under restarts/concurrency, no refresh-driven mutation, and correct UI attribution and outcome. Existing continuations must demonstrate progress and preserve the owning service's checks. Verify mixed-version refusal and keep a compatible runtime available after a proof-bound OCR successor has been created, since an older binary can refuse that successor. Guided cases must demonstrate exact scope and permissions, stale preview and duplicate submission, downstream progress and accurate prerequisite wording. Check actions on Overview, source details and Activity with a keyboard at narrow and desktop widths.
