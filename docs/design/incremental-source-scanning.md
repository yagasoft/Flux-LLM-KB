## Purpose and decisions

Detect ordinary source changes without repeatedly enumerating the whole source or reading unchanged source and retained content. Keep correct publication, recovery from missed notifications, physical-path restrictions and honest freshness reporting.

The user selected configurable weekly full checksum verification and asked for low disk pressure. They also asked us to consider NTFS journal tracking as a way to remove routine full scans. The proposed implementation uses the journal as the primary change detector for entries whose future-change boundary is proved, filesystem notifications as advisory hints for those entries, and paced full scans for baselines, recovery and weekly integrity verification. A native qualification disproved the earlier assumption that a caught-up cursor alone establishes future-change detection: unsealed entries require continuing scoped fallback work. ## Alternatives

| Approach | Benefit | Limitation | Decision |
|---|---|---|---|
| Longer cadence only | Small change; fewer bursts | Still reads every file and turns one edit into a root scan | Rejected: does not meet the request |
| Targeted watcher paths plus metadata reconciliation | Simpler native integration; inexpensive routine checks | Still enumerates periodically; weak metadata can miss preserved-timestamp edits | Degraded fallback, visibly identified |
| Journal-first tracking plus targeted scans and weekly verification | No routine tree walk for proved sealed coverage; detects writes independently of timestamp equality and watcher delivery | Requires per-entry change boundaries as well as cursor/namespace tracking; unknown or unsealed entries retain scoped fallback | Recommended with the sealing correction below |

The user additionally requested an operator-time increase of the existing E: and I: journals to 1,024 MiB each. That narrow capacity change is included below; runtime journal mutation, journal deletion/recreation, IIS elevation, OneDrive configuration changes, model downloads, pagefile changes and dashboard page relocation remain outside scope. The source manual and its rendered assets remain untouched.

## Behaviour visible to the user

| Situation | Work performed |
|---|---|
| Healthy journal and proved sealed entries between authority reconciliations | Bounded journal metadata polling; zero source enumeration and zero source/retained content reads |
| Independent authority reconciliation | Paced names/metadata and current access checks; reuse qualified unchanged content without reading source or retained bytes |
| Unknown or unsealed change boundary | Preserve scoped hints and durable paced forced checks for those entries; sealed siblings remain unread |
| One content edit | Validate and capture that file, retain/converge it through the existing pipeline, and publish the result; unrelated files are not opened for content |
| Metadata-only change | Check identity, scope, availability and policy for the affected entry; reuse previously verified bytes only when journal coverage proves no content change |
| Rename or directory move | Reconcile old/new paths or the affected subtree; never infer that every unvisited sibling was deleted |
| Initial activation, changed scope or lost journal history | Establish a paced, fenced baseline; expose partial per-entry coverage and unresolved namespaces until recovery is complete |
| Journal unavailable | Use targeted watcher work and the existing configured reconciliation cadence with metadata-first checks; expose degraded detection and weekly verification debt |
| Weekly verification | Read and checksum the baseline source content and retained blobs in low-priority, resumable batches within a configurable window |

All normal filesystem roots, including locally available cloud-backed content, use the same mechanism. Git roots also reuse unchanged bytes, but continue reading the tracked membership index at the start/end of a reconciliation batch. Git index/control changes may require comparing the complete membership list; this is not a walk or content read of every working file. Outlook and other non-filesystem ingress are outside this change.

The configured 15-minute reconciliation cadence remains an independent metadata/authority backstop. File sealing does not prove future directory or ancestor security/reparse/cloud-membership history: a controlled persistent-directory-reader probe reproduced a second distinct ACL change without a new SECURITY_CHANGE record, while the no-reader control passed. Use the existing root NamespaceMetadata pipeline for that reconciliation rather than adding directory/ancestor mutation. This is names/metadata and current-authority work, not a full-content baseline. Quiet cycles between reconciliations enumerate nothing. Every Git root also checks stable tracked membership even without in-root work, because linked-worktree control hints can be missed. Notifications wake catch-up sooner. Durable content work retains a two-second quiet period and 30-second maximum debounce measured from the first outstanding change. Track authority/Git, baseline/degraded and weekly deadlines independently from ordinary targeted completion.

Pace managed entry processing and file metadata/reuse checks at a configurable starting rate of 64 entries/second, with bounded credit. Controlled native tests showed that even a metadata-only descendant handle with read/write/delete sharing can block an ancestor rename. Buffer one directory's native names promptly in a bounded-memory burst, then dispose every cursor and ancestor handle, including the outer root lease, before pacing, processing buffered names or recursing. Limit each directory buffer to 65,536 entries and 16 MiB of accounted names/entry overhead; exceeding either limit leaves explicit incomplete/deferred evidence. Reacquire current list access and validate the original physical directory/root, path, reparse policy and cloud membership before the next managed batch after a pause, and again at final validation. Native pages retain short guards including EOF, query their original cursor and use no-recall/no-expand flags SL_RESTART_SCAN=1 and SL_RETURN_ON_DISK_ENTRIES_ONLY=8. Buffered names are discovery hints; EOF is not an atomic namespace snapshot or future-change proof. Retain finite namespace generations, per-file authority, individual absence and newer pending work. Measure the largest directory's native burst and rename latency separately; native enumeration is not paced at 64 entries/second. Baseline, capture, preview and absence guards retain their existing policy.

## Intake choice and lifecycle

Use bounded, non-waiting reads with coalesced advisory wakeups for this release. One serialised intake owner per approved volume consumes the durable cursor; it is shared by all sources on that volume. Start with the configurable two-second poll interval, then measure metadata/native calls, SQL writes and lag in staging. Polling does not mean zero metadata I/O. Fair rounds and bounded page/time budgets must allow every volume and due pending work to progress; continue catch-up promptly when backlog remains without spinning at an unchanged cursor.

A permanent asynchronous `FSCTL_READ_USN_JOURNAL` wait is technically viable but is deferred. The API waits on volume-wide, reason-filtered records, not registered-source paths. Unrelated activity can wake it, including application/checkpoint writes when stored on that volume; this is a possible feedback cost, not a measured incident. No sub-second detection requirement currently justifies changing the helper's ownership and transport lifetime. The required savings come from avoiding unchanged content reads and tree walks. Reconsider waiting intake only if measured polling cost or a new latency requirement warrants it.

The selected native mode uses `BytesToWaitFor=0`, `ReturnOnlyOnClose=0` and bounded pages, accepting both change and close records. Microsoft explicitly states that zero bytes returns at journal end, that synchronous timeout intervals may repeat, and that `Timeout` is ignored for asynchronous handles. The V0/V1 pages also contain a contradictory later example; qualify the selected mode with an isolated native test instead of copying that example. See [READ_USN_JOURNAL_DATA_V0](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-read_usn_journal_data_v0) and [V1](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-read_usn_journal_data_v1).

Lifecycle requirements:

1. After database readiness and deployment holds, validate configuration/approved volumes, query identity/readable bounds and catch up from the last accepted cursor without relying on watchers. Atomically enrol new/recovering root epochs before the shared reader can pass their starting cursor.
2. Claim outside native I/O, read a bounded page, and atomically accept relevant aliases/namespace obligations or a recovery marker with the returned continuation cursor. Process all records even when pending work already exists or no source is affected. A no-progress read releases its current lease, then waits for a coalesced wake or timer. Wakes cannot defeat fairness or burst limits.
3. Dispatch only due durable work. Intake errors are isolated per volume; an unavailable volume must not prevent another volume or already durable fallback work from running. Periodic health and Git membership checks remain independent of notification delivery and successful targets.
4. On cancellation, deployment hold or lost ownership, stop issuing new reads/claims, finish or cancel the bounded in-flight operation, and leave unaccepted pages replayable. Recheck lease, registration and epoch authority before acceptance. Restart resumes accepted cursors and immutable manifests; acknowledgement uncertainty never causes a cursor skip. Release an owned claim when safe or allow its fenced lease to expire.

Keep the helper's short query/read RPC, bounded frames, approved volumes and independent repair capability. Its existing three-second deadline bounds protocol waits, not a stalled kernel call. Cancellation checks around synchronous `DeviceIoControl` do not cancel an in-flight call; do not add a nonzero wait threshold behind that contract or claim hard native deadlines. Bounded operation ownership must prevent replacement calls/tasks from accumulating after a timeout, and native-stall health must be visible. If cancellable overlapped I/O is used for a bounded call, retain its handle, input/output buffers and `OVERLAPPED` until final completion, including cancellation races. [DeviceIoControl](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-deviceiocontrol), [CancelIoEx](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex).

If waiting intake is later selected, require an explicitly reviewed helper contract: catch up non-waiting, arm one overlapped wait per volume with a small nonzero byte threshold, handle immediate/pending completion, commit before rearming from the accepted cursor, retain periodic health, and cancel/observe completion before disposal. Use renewable fenced ownership or an advisory subscription separate from short durable read claims. Provide bounded per-volume resources and a control path that progresses while another volume waits; separate connection/frame deadlines from wait lifetime. Disconnect, shutdown, ownership loss and restart must fence duplicate subscriptions. The current single-client helper and unrenewed 30-second read lease cannot host that lifecycle unchanged. Ordinary same-volume watcher events add little when a wait is already outstanding and must not cancel/rearm or duplicate it.

## Journal access and scope

Use the documented NTFS journal API. First prove access under the restricted staging worker identity. Do not depend on undocumented/unverified unprivileged IOCTL behaviour. The implementation must not grant administrator rights to IIS or enable backup/restore privileges there.

Provide a separate, read-only journal capability in the existing protected source-helper host if direct documented access is unavailable. Keep its pipe/protocol and authorisation separate from ACL repair: enabling journal reads must not enable repair. The helper accepts only configured volume identities, bounded cursor ranges and fixed query/read operations. It cannot create, resize, delete or stamp a journal, open source content, run commands, change ACLs or accept arbitrary IOCTLs. Retain local-only pipe ACLs, verified caller SID, protocol version, frame/page limits, timeouts and protected configuration.

The journal client requests individual data, attribute, permission-read and synchronisation rights, without generic write or pipe-instance creation permission. Authenticate SYSTEM ownership on the connected local pipe handle before sending any request bytes; owner mismatch or a native owner-query failure is helper unavailability and cannot advance coverage. Reuse the repair client's native owner-query implementation. Identification does not delegate source access. The same absolute three-second deadline includes connection wait, framing and response/acknowledgement; every attempt owns and disposes its connection. This follows [Microsoft's named-pipe access guidance](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights). A test-only expected-owner override is internal and cannot be configured at runtime.

**Security trade-off to approve with this design:** reading a volume journal exposes file-change metadata for that approved volume, including entries outside registered sources. The trusted helper/indexer may inspect that metadata transiently to route records. Persist and expose only registered-source entries; discard unrelated names, never log raw pages, and reject unapproved volumes. This is broader metadata visibility than a folder watcher and must be explicit in configuration, deployment review and tests. The helper must not claim it is a folder-only journal API. A more restrictive helper-side namespace filter would duplicate authoritative state and is not added speculatively.

Read each approved volume through one bounded intake owner rather than once per source. Share its durable volume cursor, schedule volumes fairly and bound catch-up bursts. Existing root no-follow policies remain the sole authority for opening source content: a journal record is a hint about an identity, not a capability to read its path.

## Existing journal capacity increase

The authorised implementation includes the specifically requested in-place increase on **E: and I: only**: `MaximumSize=1073741824` (1,024 MiB) and `AllocationDelta=134217728` (128 MiB), 32 times the observed target capacity. The design-time free-space check found approximately 21.3 GiB on E: and 596.1 GiB on I:, making this a reasonable starting allocation. These are observations, not reserved space. The NTFS target is not a hard maximum and a larger setting does not immediately fill the journal with historical records.

Implement this as an independently reviewed operator step, separate from the runtime helper. Before mutation, resolve the exact volume identity behind each drive letter, verify fixed NTFS, an active existing journal, no deletion-in-progress, the expected journal identifier and current cursor bounds, and at least 2 GiB available space. Save a receipt with original maximum/delta and readable range. Refuse a missing/replaced volume or missing journal; do not use this permission to create a new journal. Do not reduce an already larger setting changed by another operator: preserve it and report the difference.

The intended commands, only after those guards, independent operational review and deployment coordination, are:

```powershell
fsutil usn createjournal m=1073741824 a=134217728 E:
fsutil usn createjournal m=1073741824 a=134217728 I:
```

Microsoft documents that `createjournal` changes an existing journal's parameters without disabling it. Re-query immediately after each volume and verify its identity, unchanged journal identifier, expected maximum/delta and readable application cursor. If continuity changed concurrently or an outcome is uncertain, stop that operation and preserve its receipt; do not retry as deletion/recreation. An application rollback leaves the larger journal in place. Automatic shrinking could discard useful records and is not part of rollback.

Measure timestamped `FirstUsn`, `NextUsn`, `LowestValidUsn` and journal ID around representative idle, indexing/build and deployment windows. Use same-ID `NextUsn` deltas to estimate append-byte rate and observed cursor headroom; label projected retention as an estimate and report the measured window. No fixed number of retained days is promised. The runtime reader remains read-only and does not resize in response to lag.

## Persistent state and transaction boundaries

Add migration-backed, versioned records using existing EF/SQL conventions:

1. `SourceVolumeJournalCheckpoints`: volume identity, journal identifier (unsigned 64-bit value encoded without signed overflow), next unread USN, reader owner/generation/expiry and row version. The cursor means **records durably accepted**, not content published.
2. `SourceInventoryEntries`: root/configuration-policy identity, normalised relative path and collision-checked path fingerprint, file/directory identity, parent identity, current revision/artifact references, metadata fingerprint, baseline epoch, last verified time and row version. Multiple paths may share a file identity; never use file identity alone as a unique path key.
3. `SourcePendingChanges`: root/path or subtree identity, accumulated reason flags, monotonic generation, earliest/latest USN and durable claim state. Keep both rename sides. Work arriving after a claim remains a later generation.
4. `SourceRootScanStates`: baseline epoch and state, covered journal identity/cursor, last complete reconciliation, degradation/recovery reason, verification policy and last verification result. Keep root-wide inventory/issue evidence separate from targeted results.
5. `SourceVerificationRuns` and `SourceVerificationItems`: immutable cycle membership (entry/revision/blob references, no content), per-item outcome and a resumable cursor. This gives finite, honest completion even when new files arrive during a weekly cycle.

A volume batch transaction fences its reader generation and expected cursor, merges relevant changes and namespace operations, then advances the cursor **in the same commit**. An ambiguous acknowledgement is retried with the same volume/journal/range identity and stable native-record evidence; transient current-path resolution is not a replay identity. A replay does not create new dirty generations, but a fresh owned no-progress claim must still be completed/released. Duplicate-work detection never authorises skipping the journal cursor or intervening records. If routing is unresolved, persist the unresolved operation or a bounded recovery marker before advancing.

Use one serialised scan owner per root. Snapshot exact pending paths/subtrees, identities, generations and recovery/coverage epoch into an immutable manifest at claim. Completion acknowledges only successfully processed manifest obligations whose pending generation still matches. An empty targeted manifest acknowledges nothing; a root-wide generation ceiling is insufficient because it includes paths still waiting for debounce or not selected. Later signals, changed bindings and failed/deferred paths survive. Retries preserve the manifest and request identity. Root disable/delete, policy changes, deployment holds and lease loss fence intake, convergence and completion under the established lock order: publication fence when selection can change, root, owned scan, identity/path, artifact, then observation/checkpoint records as applicable. Journal intake does not acquire the publication fence while doing native I/O; lock root rows in deterministic order. Perform filesystem I/O outside SQL transactions except the existing bounded final authority checks.

Coalesce unclaimed work by volume/journal and recovery epoch, physical file identity and root/path alias, preserving both rename endpoints and accumulated reasons. A later real USN or degraded watcher generation remains distinct from in-flight work, even for the same file. Source capture can avoid a subsequent reread only with an explicit stable identity/epoch/post-acquisition barrier receipt proving that the range was covered; equal metadata or presumed notification equivalence is insufficient. Otherwise capture conservatively again. Journal records and watcher notifications are not individual human saves; no exactly-one-content-read-per-save guarantee is made.

Page reads and writes at 512 entries. Cap an in-memory journal page at 1 MiB, validate record lengths/versions/UTF-16 boundaries and support the advertised V2/V3 layouts; unknown versions/reasons produce an explicit recovery decision, never silent skipping. Cap per-root accumulated distinct pending paths at 10,000; overflow becomes a durable `BaselineRequired` marker rather than dropped changes. The volume reader may continue for other roots after safely marking the affected root. These bounds are proposed defaults to validate in staging, not benchmark results.

## Establishing and preserving coverage

For each initial/recovery baseline:

1. Atomically enrol the new/recovering root epoch under the shared volume cursor/reader fence, including its admitted root and ancestor identities. Establish starting cursor S in that transaction before enumeration. Increment a registration generation; accepting an already-read page must recheck that generation and route for newly enrolled epochs before advancing. Start durable intake from S immediately. While the namespace map is incomplete, retain relevant unresolved identity/reason/parent operations or a conservative epoch recovery marker; never discard them as outside scope merely because the new root is not yet routable. Unknown names outside sources are not persisted. A crash between enrolment and enumeration resumes the same epoch and pending work. This prevents a long baseline or another root's reader from skipping S-to-E changes.
2. Enumerate in scope with existing guarded handles, record directories as well as files, and perform full content capture where no valid prior coverage can establish reuse. Do not seed trusted unchanged observations from pre-journal SQL size/mtime alone.
3. Replay/apply changes captured during enumeration, including subtree moves, before certifying coverage to a captured ending cursor E. Resolve every epoch uncertainty marker using captures/namespace evidence covering its barrier; if that cannot be proved, retain recovery state and repeat the affected baseline work. Recheck root policy, journal identity/retention range and owned generation. Concurrent changes after E remain durable pending work.
4. Mark the baseline complete only after complete namespace coverage and successful authority checks. An incomplete baseline may enter `JournalPartial`: a file gains per-entry reuse authority only after stable capture and the required journal-barrier checks, while unavailable paths/subtrees remain durable deferred discovery. Observing a directory does not prove complete child membership. Partial completion cannot authorise whole-root unseen withdrawal or clear unrelated issues. Metadata retries do not certify content; dirty/untrusted files require capture when accessible. Weekly verification retains unresolved outcomes.

Journal identifier mismatch, cursor below the readable range, impossible cursor regression, unsupported records or unresolvable in-scope namespace history invalidate the affected coverage. Do not simply jump the cursor or treat metadata equality as proof across the missing interval. An atomic reset may establish a new starting cursor only together with durable coverage invalidation, a new recovery epoch and a queued paced baseline, including when there are no ordinary pending paths. Refresh ancestor registration for that epoch. Unsupported records/native gap errors must reach this recovery decision rather than repeat generic unavailable retries. An older scan cannot promote a newer invalidation to healthy; fence completion against the recovery/coverage generation and retain intervening markers. Incomplete `BaselineRequired`, `Baselining` and `JournalPartial` namespaces all retain uncertainty for every potentially affected entry. Full content verification is required where continuity is lost; preserve prior publication and mark freshness uncertain until proofs are rebuilt. Display-name/schedule-only changes need not discard content proofs if their content-policy fingerprint is unchanged.

Filesystem notifications preserve bounded normalised current/old relative paths, file/directory uncertainty and overflow. Validate strings lexically on ingress and physically before access. While journal coverage and the affected entries' sealed change boundaries are healthy, hints only wake intake/dispatch; they never independently release content scans or create content-dirty generations. Unknown/unsealed entries retain force-capture hints in the same durable pipeline. A watcher-first hint may cause an empty read before its journal record exists; later intake still accepts that record. Journal-first followed by advisory watcher noise adds no second hashing obligation. Watchers remain useful for faster bounded-poll wakeups, unsealed/degraded paths, Git control changes and recovery/health hints.

When journal coverage is unavailable, merge watcher content hints as force-capture generations into the same durable pending pipeline even if metadata matches; retain rename endpoints and use the paced reconciliation backstop for missed hints/overflow. Keep the last cursor. On continuous-history restoration, replay it fully and retain unproved fallback work; a degraded capture may legitimately be read again without a valid coverage receipt. Lost history follows the new recovery epoch/baseline rules. An overflow requests catch-up first; it requires recovery only where coverage cannot be proved. This change removes the watcher's separate healthy scan-scheduling path rather than adding a second processor.

The independent recovery review requires explicit separation of availability, baseline debt and namespace debt. Entering `Fallback` preserves any required baseline. Coalesce invalidation while recovery is only required, updating its boundaries/generation; a new gap or ancestor-authority loss after recovery starts fences the running baseline. Versioned manifests retain their owned claim and recovery generations. A valid retry stays frozen; only a higher owned claim may replace a manifest invalidated by recovery or journal-to-fallback availability change, retaining the request and all unacknowledged obligations.

Unresolved parent identities under an incomplete namespace create a bounded, generation-fenced metadata/membership obligation after known identity/alias/parent routing. Use a known uncertain subtree or root scope, and the reconciliation backstop rather than repeated immediate walks. They do not repeatedly invalidate content epochs. Directory failures, exhausted discovery budgets and incomplete cloud membership explicitly affect namespace completeness; an inaccessible file alone does not. A reconciliation claims a finite namespace generation and can clear it only with complete namespace evidence and a closing journal barrier. Later uncertainty survives and is paced to the next backstop; covered siblings remain reusable while namespace ambiguity persists.

Pass the immutable manifest to capture bookkeeping. After matching the capture against a guarded current source observation, obtain and drain a post-acquisition barrier before committing journal coverage under that same owned recovery epoch. Fallback captures retain an explicit unproved journal-coverage flag. Metadata reuse supplies no checksum timestamp or journal proof. Continuous restoration queues those unproved captures for conservative recapture. A helper failure between capture and barrier retries the frozen plan; it cannot certify coverage or reclassify successful retention as blocked. Root-ID discovery for acceptance and reset occurs before serializable work; ordered root locks then precede registration, reader ownership, expiry and cursor validation. The reviewer approved this focused approach without a larger architecture, subject to implementation evidence.

## Aggregation and per-entry change boundaries

A native controlled test on 24 October reproduced a repeated same-length, timestamp-restored overwrite with no new content record in `[S,E)` while another read-sharing handle kept the aggregation period open. The no-reader control did produce a record. This affects ordinary scanning after capture acknowledgement, not only a multi-lease weekly hash. A drained barrier proves the accepted interval, not that a future repeated edit must generate a fresh record. A transient RH oplock ends at retirement and cannot solve future detection. Existing optimistic version2 `JournalCovered` receipts require requalification before journal-only authority.

Keep capture correctness separate from future-change detection. Persist the latest actual per-physical-file journal position and reasons separately from OR'ed pending-work reasons; a later non-close record cannot inherit an earlier CLOSE. Update that state, scoped pending work and the durable cursor in one transaction. Known watcher hints for unknown/unsealed entries force capture through the same pipeline even when metadata matches. Capturing an entry may acknowledge its exact content generation, but not erase its continuing unsealed obligation. An eventual close triggers requalification; it cannot promote a hash captured before hidden later writes. Apply the same distinction to namespace/ancestor evidence wherever aggregation matters.

The user selected the independent Astra/high reviewer's narrowly scoped, guarded post-capture `FSCTL_WRITE_USN_CLOSE_RECORD`, subject to staging and actual OneDrive qualification. It appends journal metadata for the exact authorised file; this is the explicitly authorised exception to the original read-only application contract. Two synthetic qualifications passed: a regular local file and a hydrated disconnected Cloud Files placeholder under a restricted non-admin token. They matched the returned USN/full file identity to an actual CLOSE, preserved bytes and modification time, kept another reader open, and observed a fresh record after the later repeated overwrite. These results qualify one tested environment, not every Windows/filesystem/filter or actual OneDrive. Microsoft documents forced CLOSE but does not explicitly specify the aggregation reset demonstrated by the probes.

Capture and forced CLOSE share the same uninterrupted write/delete-excluding source guard. The capture owner opens a separate synchronous, read-only, no-follow/no-recall handle for that same physical file; it does not issue an unmanaged overlapped operation on the FileStream's completion-port handle. Refresh/revalidate the observation after sealing. Persist a version3 receipt bound to the captured bytes, full identity, journal identity, recovery epoch, qualified profile and the immutable plan generation fixed before capture acquisition, with durable cursor coverage of the exact returned CLOSE record. Cancellation during a synchronous native call requests cancellation of subsequent work; native return still owns its handle lifetime.

Track the latest actual record separately from accumulated reasons. Pending work additionally retains the last content USN and last unjournaled work generation; missing pre-journal values mean unknown/dirty. A receipt may satisfy content obligations only when both the content USN is at or before its seal and the unjournaled generation is at or before its pre-capture generation. Namespace, membership, policy and recovery checks remain independent. Consume synthetic records normally and complete only exact manifest generations. A synthetic record can leave a newer generation for a cheap reuse/completion pass, without another content read. A later real write, watcher force hint or unknown obligation remains actionable. An eventual CLOSE never promotes an old hash by itself. Native success followed by a crash or ambiguous SQL commit leaves an unproved capture until an exact durable receipt is established.

Pure NamespaceMetadata debt arriving after a scan plan was frozen does not itself invalidate a qualified file-content receipt. Continue guarded content reuse while retaining that newer namespace row, its generation and incomplete status. Keep the later-generation recapture fence for ScopedNamespace and GitMembership and keep both content cut-offs unchanged, including content reasons merged with metadata. Completion must not acknowledge a newer metadata generation or certify namespace completeness from the older sweep. This distinction prevents unrelated volume uncertainty from rereading sealed siblings without weakening discovery or deletion authority.

Continuous targeted work cannot postpone the independent authority backstop. Before freezing a fresh owned manifest, check the current durable root reconciliation deadline and include the paced root metadata sweep when it is due, even if journal dispatch queued this request first. Successful reconciliation advances the ordinary deadline through the existing completion contract. A previously frozen retry remains immutable when the deadline later passes; the next fresh manifest carries the overdue sweep. This adds no competing owner or separate scheduling path.

New seal writes default off. Use a small operator-provided qualification for each exact physical root, binding its environment fingerprint and qualification ID/scope to receipts. New roots have no implicit qualification; a synthetic provider qualification cannot cover OneDrive. Check the current Windows/architecture and kernel/NTFS/cloud-filter version fingerprint before trusting seals and during periodic health. Cloud qualifications additionally bind the exact provider name and version returned by metadata-only `CfGetSyncRootInfoByPath` on the root. Recheck them at every seal/reuse/advisory-watcher trust decision; unavailable, malformed, missing or changed provider evidence fails closed. Provider status is separate health information. Existing four-field receipt hashes are preserved only for explicitly local `local-ntfs-*` scopes and the existing `isolated-local-ntfs-staging` fixture scope; a cloud scope with missing provider fields is never interpreted as local. No sleeping while holding SQL transactions or a file handle between scheduled windows. The file/byte/time batch limits are soft between-file limits, permitting one admitted file to finish beyond them. Foreground/lease/pause/policy/window checks remain hard between chunks. Acquire it non-blockingly; never delete/recreate the lock file or steal it on timeout. SQL session loss cannot release this physical ownership. Isolated staging uses its own layout and data.

Pre-emption distinguishes new work from paced debt. Completion parks an exact failed/deferred generation using `RetryGeneration`; later journal/watcher generations make that marker stale immediately. Future pure metadata backstops and future matching retry debt do not veto unrelated reads, while due debt and fresh nonmetadata work retain priority, including during debounce.
