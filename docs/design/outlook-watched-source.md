# Outlook as a watched source

An Outlook profile captures and retains mail through the read-only desktop host. The profile owns capture identity, leases and cursors. Its dedicated watched source owns discovery, retained processing, attachment extraction, OCR and search publication.

The private capture manifest records available subject, sender, receipt time and original attachment filenames. The publisher constructs searchable UTF-8 Markdown and copies attachment bytes in their original format. Historical messages contribute their retained body and attachment bytes. Available, authenticated manifest metadata informs the export. If a historical filename is unknown, a stable name uses the supported format where the evidence identifies it. Missing historical headers are omitted.

Each accepted capture owns one stable bundle directory. The publisher writes a complete stage outside the watched tree on the same volume. The database pins the stage and its file identities before the atomic directory move. After interruption, the next worker resumes that stage or verifies the installed bundle and acknowledges it without rereading Outlook or rebuilding metadata. The Outlook page shows the last successful export and links to ordinary source progress.

## Cutover

1. Prepare matching web, Outlook host and CLI binaries. Use `scripts/deploy/update-native-iis-incremental.ps1 -PlanOnly -ApplyOutlookWatchedSourceMigration` to review the exact database incarnation, migration history, SQL hash and payload bindings. Supply the reviewed installed payloads for plan inspection and the reviewed candidate payloads for Apply. The updater stops the hosts, preserves helper policy and task settings, applies the one schema 80 to 81 migration and verifies the new schema before activation. Keep the spool, configuration, previous binaries and migration evidence.
2. Provision a dedicated empty source directory and a separate empty staging directory on I:. Restrict both to the identities that operate this source. Register the destination as an ordinary recursive filesystem source with no path filters or link following, in the normal dashboard. Keep broader roots clear of both locations.
3. Review the exact capture/profile and source IDs, staged representative results, and the intended backlog. Use the local CLI command `outlook-watched-source bind --configuration <private.json>` with a private JSON file containing `ProfileId`, `SourceRootId`, `WatchRoot` and `StageRoot`. The command stores the physical directory identities and refuses a populated or already used destination. An enabled destination starts the export worker on its next pass.
4. Each old message stays in the previous search route until its entire bundle is staged. The publisher records the cutover receipt and withdraws the precise previous revisions under the publication fence, then moves the complete bundle into the dedicated source. The normal source pipeline admits it. This can cause a short search gap while the new copy indexes. The publisher preserves spool data, including data for blocked exports.
5. Release the dedicated source's held initial scan through **Save and scan** on the same reviewed source configuration. A source added after startup can wait until the next watcher registration cycle. After the first export backlog has drained, check that every exported message was discovered. If the first scan missed later arrivals, use **Reconcile source metadata** once on the dedicated source.
6. Verify the source link, last export, cited message text and representative attachment extraction or OCR. Check that the recorded previous revisions are suppressed. Report what is still indexing and any formats the pipeline cannot parse.

## Rollback

Run `outlook-watched-source suspend --profile <guid>` using the schema 81 CLI to restore the previous publication route. The operation pauses the dedicated root, withdraws its published revisions and restores the prior suppression values owned by the cutover under one publication fence. It preserves watched bundles, captured mail, cursors and private receipts. Keep schema 81 and its matching binaries in service. Readiness requires the compiled migration set, so any binary replacement must also support schema 81. After an uncertain migration or activation failure, retain the owned hold and reconcile the exact schema, payloads and receipts before recovery. Mail captured while the watched route was active remains retained and can be replayed after the route is restored. A suspended watched source cannot be resumed through ordinary source controls.

Test cutover and rollback in isolated staging before authorising production execution. Treat a missing retained sidecar or a directory identity mismatch as failed publication. Keep ready manifests and staged bundles while any acknowledgement is pending.
