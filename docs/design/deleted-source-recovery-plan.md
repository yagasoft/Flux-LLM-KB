# Deleted source recovery: design and implementation plan

Date: 31 October 2026. Baseline: `670192d5`. Design owner: Astra; implementation owner: the main agent. This document implements the user's request to design, implement, deploy and validate deletion recovery. It is not a record of tests or deployment having passed.

## Outcome and boundaries

When a file or directory disappears, FluxKnowledge promptly verifies the affected paths, suppresses the obsolete source revisions, prevents new work and publication for those revisions and their derived inputs, and requests cancellation of running work through its existing owner lifecycle. Offline deletions receive the same treatment before affected retained work resumes after startup. An unrelated capture failure must not prevent verified removals.

The first executable result is: register and scan an isolated source through the existing command/service interfaces, delete one indexed file, accept its change through the journal/watcher interface, reconcile removal, and observe suppression plus refusal of its queued work without waiting for another file's capture to succeed. SQL and file operations use the existing disposable integration harness. No real models are needed.

Keep SQL Server canonical, the existing journal cursor/dirty-path transaction, physical absence guards, publication fence, and native cleanup ownership. Do not purge retained content, change public API contracts, update the user manual, alter unrelated overview/search work, download models, or process dead letters. Removal recovery reuses the existing pending rows, reason bitfield, generation fences and source suppression. Production-scale publication qualification subsequently demonstrated the need for the additive metadata index described under bounded activation proof; it changes no canonical content or public API.

Production implementation-owner scope is the authorised incremental update and validation of local FluxKnowledge IIS at `http://127.0.0.1:5137`, installed at `I:\FluxKnowledge\App`. Design analysis itself performs no production operations. Ordinary tests remain isolated from production credentials, bindings and mutable data.

## Why this design

`SourceChangeJournalService` already pumps the journal at startup. `SqlSourceChangeJournalStore` atomically persists routed work and accepted cursor. Adding another watcher or replay subsystem would duplicate those mechanisms. The missing capabilities are independent removal progress, admission ordering and consistent source eligibility.

Full successful baseline scans as the prerequisite for removal are too coarse: `SourceScanWorker` reaches `CompleteAsync` only after capture work. Increasing the pending-path cap postpones overflow without fixing its repeated invalidation of scan authority. Mutating immutable source identities or dropping their uniqueness guard would damage provenance. Reuse verified logical owners, coalesce durable obligations and use current physical absence evidence instead.

## Invariants and concrete decisions

### 1. Logical revision identity and replacement files

Keep the unique `(SourceRootId, CanonicalPathFingerprint, ContentSha256)` contract. An original filesystem source at the exact ordinal path with identical hash and byte length may reuse its one existing logical revision even when the current physical file identity changed, but only under the already established `authoritativePhysicalCapture` conditions in `SqlSourceScanStore`: owned current scan, live matching `ISourceCaptureLease`, current admitted root/configuration, no followed links and exactly one link. Require `OriginKind == 0`, exactly one exact owner, and the existing wider case-ambiguity check. Revalidate the live capture before commit.

Keep revision ID, immutable `StableSourceIdentity`, revision history and existing artifact immutable. `RecordCaptureAsync` updates the inventory's current physical identity; current discovery evidence records the current capture. The immutable identity describes the logical retained revision's original provenance, not a claim that the current file still has its original NTFS identity. If an artifact exists, retain the current exact hash/length/store-path consistency checks. A missing artifact is recoverable using the fresh matching verified receipt; this must not strand an earlier retention-blocked row. Receipt-less, unowned, linked, derived or ambiguous adoption remains refused. Existing Git adoption remains unchanged.

### 2. Overflow represents work instead of restarting it

Add `SourcePendingReasons.FullRecapture = 1L << 35` and `RemovalPending = 1L << 36`. Use one small shared SQL pending-work merge/coalescing helper from journal acceptance, watcher fallback and the unproved/unsealed overflow paths.

On queue pressure, transactionally replace the detailed pending set with one normalised `.` subtree obligation containing `FullRecapture | NamespaceMetadata | RemovalPending`, plus the conservative union of prior reason flags. Preserve the earliest nonzero `FirstUsn`/first observation, latest `LastUsn`, maximum known `LastContentUsn`, and force `LastUnjournaledGeneration` to the newly allocated state generation once at the initial collapse. Unknown provenance stays forced work. Set it due now. While this full-recapture row exists, merge later incoming work into it instead of recreating thousands of children. Later attributable journal pages preserve that unjournalled boundary and raise `LastContentUsn` only for real content changes. Pure CLOSE/BASIC_INFO records, including the scan's own closing records, must not repeatedly move the forced-capture boundary. New watcher/unattributed content hints can raise it. Row generation still fences acknowledgement; namespace generation changes only for actual namespace uncertainty, not every harmless journal page. Never acknowledge a cursor or watcher batch unless its work is represented by that row in the same transaction.

Initial queue-pressure coalescence does not call `InvalidateCoverage`: it increments namespace generation and leaves namespace incomplete, but does not change baseline epoch/recovery generation or invalidate an active capture manifest. Real journal resets, root/ancestor identity changes and policy changes still use the existing authority invalidation. `ContentObligationCovered` must explicitly require a capture receipt whose capture generation is at least `LastUnjournaledGeneration`, and a seal USN covering any `LastContentUsn`, for the `FullRecapture` obligation; metadata enumeration alone cannot satisfy it. A frozen manifest cannot remove a later-generation row, and a changing namespace cannot be reported complete. Existing successful individual capture receipts remain reusable when they actually cover the frozen obligation. Add a regression with scan-generated CLOSE traffic: already captured files remain reusable and the next quiet pass discharges the coalesced debt.

### 3. Independent guarded removal reconciliation

Introduce an application port `ISourceRemovalReconciler` with `ValueTask<int> ReconcileAsync(CancellationToken ct)` and a SQL implementation in `SqlSourceRemovalReconciler.cs`. It processes durable `RemovalPending` paths/subtrees independently of source scan leases and file capture. Mark journal delete/rename namespace scopes and conservative watcher/unknown scopes for removal reconciliation. Mark existing pending scopes during startup, so old rows receive the new handling. Normalise paths with existing helpers and do not trust raw event paths.

Reuse/extract the suppression transaction from `SqlSourceIncrementalCoordinator.Completion.cs`: acquire publication fence, root lock, verify enabled/configuration/physical root authority, select exact currently unsuppressed original revisions in the declared path scope, acquire `OpenAbsence` leases, validate immediately before commit, set suppression/retention witness, and advance publication selection. This reconciliation does not need a successful content scan or its manifest. Its own authority is the current root plus live absence leases. A directory event examines retained original revisions below the directory, including descendants without individual watcher events.

Do not suppress from `File.Exists == false`, watcher reasons, inaccessible parents, cloud-placeholder uncertainty, unavailable volumes, root substitution or incomplete namespace. A recreated path makes `OpenAbsence` return no absence proof; the old event cannot suppress the new successor. Present files remain capture obligations where required. For this removal pass, a safely observed present path is not a deletion; content supersession continues through verified capture.

Process candidates in SQL keyset pages and bounded transactions, holding physical leases only for a transaction's small batch. Suppressed rows and publication changes are durable progress. A local paging cursor may be lost on restart: restarting repeats harmless presence checks and skips already suppressed rows. Do not add a durable cursor merely for this optimisation. Run the removal worker separately from journal intake so a large root does not stop cursor acceptance; use bounded turns/fairness across roots. If a turn yields, retain its local cursor; after process restart re-enumerate safely.

`RemovalPending` is owned by this reconciler: capture completion must not silently delete it. Clear that bit only with an exact pending generation comparison after all candidates in the claimed scope were checked. Preserve all content/namespace obligations. If only this bit remains, removing that exact row is allowed. For a whole-root pass with isolated uncertain paths, atomically move the unresolved removal obligation to those paths before clearing the root's removal bit; do not erase or acknowledge its other flags. If scope changed during the pass, leave its newer generation pending. Repeated signals therefore cannot erase unprocessed work.

Per-file capture failures remain recorded as scoped deferred evidence. Catch only identified source-local conflicts/failures; lease loss, transaction/infrastructure faults and root/journal authority changes still stop that scan. Independent removal must work even when such a scan cannot reach completion.

### 4. Effective source eligibility and native cancellation

Create one SQL eligibility helper, `SqlSourceWorkEligibility`, used by the relevant stores rather than several subtly different predicates. Eligibility requires an undeleted current pipeline revision, unsuppressed retained input, enabled source root, unsuppressed original owner for a derived input, an admitted process/root at startup, and no covering unresolved `RemovalPending` scope. Use normalised exact path or directory-boundary prefix comparisons; a path such as `a` must not cover `ab`. Resolve the original owner's physical path for derived inputs.

`ParentSourceRevisionId` is overloaded: for `OriginKind == 0` it can describe revision history. Stop at that original owner and do not suppress it because a historical predecessor is suppressed. Support the existing finite ownership shapes `1 -> 0`, `2/3 -> 0`, and `2/3 -> 1 -> 0`. Require every intermediate owner to remain unsuppressed and within the same root, and apply removal scopes to the final physical owner's path. Reject malformed lineage rather than guessing; fixed joins are sufficient. Add an intermediate archive-owner regression and do not introduce a generic ancestry engine.

Apply the predicate at job/outbox claim, retained branch admission/enqueue, GPU ready selection, embedding/OCR execution claim, checkpoint/result commit and publication/requeue. Existing maintenance/rebuild exceptions may relax root pause policy only as already authorised; they cannot bypass suppression, missing owner or deletion-reconciliation holds. Ensure all claim/commit checks participate in the same transaction/lock boundary as suppression. Follow publication -> root -> source/work lock order; avoid adding a source read before a publication lock that creates an inverse order. A preflight check outside the claim transaction does not close the race.

Treat persisted suppression as durable cancellation intent. A bounded recovery pass can rediscover affected active embedding/OCR tasks and request cancellation using `EmbeddingGpuExecutor.RequestCancellation` and `PaddleOcrVlmExecutionRegistry`, following the existing `SqlSourceDeletionStore` cancellation pattern without invoking root deletion. Retry delivery of cancellation after missed prompts. Recheck source eligibility after local cancellation registration and before native execution, closing the registration race. No longer eligible results are rejected even if native cancellation arrives too late.

Queued jobs/activities and Ready GPU tasks proven never admitted can become terminal with a source-suppressed reason; use existing terminal states. Do not mark a delivery dispatched, increment native cleanup confirmation or release a capacity slot to manufacture proof. Active/previously admitted tasks retain their lease, ownership and native-cleanup evidence until the existing adapter lifecycle settles them. Cleanup and owner-exit recovery must remain runnable even while source admission is closed. Once real cleanup settles, terminalise obsolete parent work instead of leaving it apparently processing or requeueing it.

### 5. Startup admission: process gate plus durable scope obligations

Add a process-local `ISourceWorkAdmission` singleton that defaults to closed for every source root on every process start. A root is never admitted merely because another process previously reached ready. The source journal/removal startup coordinator captures one finite journal high-water point per enrolled volume, drains through it using existing leased cursor logic, ensures durable `RemovalPending` obligations for affected/existing pending scopes, and performs an initial removal pass. The gate then admits the root while SQL eligibility continues to block any unresolved paths; an inaccessible path need not block a separate root or unrelated path.

For missing enrolment, journal gaps, helper unavailability, disabled journal mode or unproved routing, persist a root-wide removal obligation and examine existing retained original paths with the same physical guards. This metadata/removal pass does not certify full baseline/content coverage. True gaps keep baseline recovery required. Once verified removals and unresolved per-path obligations are durable, unaffected work can resume while ordinary capture/baseline recovery continues. Root-wide uncertainty remains a root-wide hold.

Implement startup coordination in a dedicated hosted service registered even when journal mode is disabled; do not rely on hosted-service registration order or `BackgroundService.StartAsync` as the barrier. Journal intake, source scanning and native cleanup are not held behind this gate. Every CPU/GPU dispatch path that can initiate retained source work must consult the same gate, including direct store/CLI composition. A read-only CLI need not run startup reconciliation, but a CLI worker cannot default to unrestricted admission. Newly registered roots start closed until initialisation. Use an immutable admitted-root snapshot as a parameter to SQL claim predicates; actual suppression/pending scope checks remain durable in SQL. No database 'ready forever' flag is introduced.

The high-water barrier covers changes known at startup. Later filesystem changes follow the normal journal/watch reconciliation latency; do not claim zero-delay detection or linearise SQL against all future external filesystem mutations.

## Bounded activation proof

Whole-root activation keeps the existing serializable transaction, publication fence and atomic pointer change. Each equality command compares a window containing at most 16,384 distinct raw or staged vector IDs. Phase 0 takes raw keys from the current membership ledger for the candidate corpus epoch; phase 1 takes raw keys from vectors. Both phases merge those keys with their staged keys and freeze the high-water mark across both populations. Staged-only keys, gaps and keys beyond the raw maximum must remain visible. An empty eligible window is not exhaustion.

Both sides use the same exclusive lower and inclusive upper bounds. Keep the existing byte-length and binary checksum comparisons, source identity, nullable owner/root comparisons and final canonical count equality. The fence remains held between windows and through activation. Phase 1 builds a session-local `#RootEligibleArtifacts` table once inside that same serializable transaction. It uses the shared publication predicate with only the chunk-revision comparison deferred to the vector/chunk join. The map preserves original and derived ownership, suppression, deleting-root and latest-publication rules. Each bounded vector window still checks chunk and vector revisions, content hash, nullable search-input hash and deletion status. Normal completion drops the map; cancellation or failure rolls back its creation with the owning transaction. Every retry creates a new map.

The additive EF migration `20261101195325_AddVectorPublicationMetadata` creates the non-unique, unfiltered `IX_Vectors_PublicationMetadata` index on `VectorId`, including only `TextChunkId`, `SourceRevision`, `PayloadChecksum`, `TextChunkContentHash`, `SearchInputHash` and `IsDeleted`. It excludes vector payloads. Qualification observes a physical, enabled index and verifies that actual equality plans with non-empty staged membership use it without wide-row lookups.
